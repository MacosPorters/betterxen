## Placement and resource correctness

| Evidence | Independent expectation and assessment |
| --- | --- |
| WB mapped CPU pointer alignment | Microsoft specifies alignment for heap-relative placement. Nothing in the Map contract equates CPU and GPU virtual addresses or makes the CPU address 64 KiB aligned. In A's two raw buffer-alias runs, CPU pointers ended in `4000` modulo `10000` (hex). That is 16384 modulo 65536. The GPU VAs were multiples of 65536. Independently written B placement code reproduced the distinction on M5. |
| Two invalid creations | A's 64 KiB buffer at offset 1 is misaligned and its allocation span also exceeds the heap by one byte. The aligned offset 65536 lies at the end of the 64 KiB heap and leaves zero bytes for the nonempty buffer. A's two M4 logs show successful returns for both and E_INVALIDARG for a texture on a buffer-only heap. A submitted neither invalid buffer. B separately reproduced the buffer returns on M5. Compare against a valid offset 0. |
| Same-offset buffer aliases | The placed buffers have the same known layout, while the guard range is wholly disjoint. The advanced-model alias barrier orders the write and second resource's COPY_SOURCE read in one submitted list. The explicit COMMON transitions scope each use, the fence follows all copies, and the guard exercises a displaced range. The expected pointer and GPU VA deltas are 0 and 65536 respectively. The two raw runs show the correct deltas and 16384/16384 for each of source, inherited and guard readbacks in each of three rounds. The seed steps 0x101 each round and 0x10000 each session. These results demonstrate application-visible addresses and GPU data inheritance for these whole-buffer ranges. The backend's backing pages and arbitrary CPU aliases remain unresolved. |
| Mixed mip textures | The three mips have dimensions 65×37, 32×18 and 16×9, totaling 3125 texels. This yields 3125 useful bytes for R8_UNORM and 12500 for RGBA8 or R32_UINT. Distinguish 512-byte copy-placement offsets and 256-byte row pitches from allocation alignment and actual texel widths. WB/WC use per-mip Map with null output and WriteToSubresource in COMMON. DEFAULT uses a staged copy. The readback transition and fence are explicit, and guard writes finish before the subsequent steps. Both raw runs record all nine useful-byte and guard checks exact. Byte count excludes padding. The test does not assert texture sampling or raw texture Map pointer results. |
| RGBA8 and depth alias clears | The fixture activates each RT/DS alias and then clears in RENDER_TARGET or DEPTH_WRITE, respectively. Readbacks are distinct and the transition to COPY_SOURCE orders the transfer. RGBA8 clear tuples are (1,0,1,1) and (0,1,1,1), equivalent to little-endian words 0xffff00ff and 0xffffff00. Depth 0.5 and 0.25 correspond to 0x3f000000 and 0x3e800000. Both M4 logs show 2405/2405 per alias for WB and DEFAULT. Each alias is reinitialized. This tests separated activation and clear, so it leaves texture data inheritance, stencil and rasterized depth open. |

[Microsoft placed resources](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12device-createplacedresource), [buffer footprints](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12device-getcopyablefootprints), [memory aliasing and data inheritance](https://learn.microsoft.com/en-us/windows/win32/direct3d12/memory-aliasing-and-data-inheritance).

One harness limitation: A's normal successful runs wait before object teardown. After a fence failure, the shared Queue helper throws with possible outstanding work, unwinding local resources before the parent terminates the guest. That error path should use explicit retirement or disposable-process teardown in future fixtures. It does not change the reported results with valid fences.

## Physical accounting

The corrected A2 source retires allocation, command and shader objects, then releases the device. It also includes truly CPU-only and graphics-warmed CPU controls. That materially improves the earlier release checkpoint. The A2 bundle contains 12 completed cases and an interrupted later case. A22 includes a second distinct pressure stop and cannot be pooled as a full repeat of A2.

A's three in-stage readings are correlated samples within one process. The 64 MiB heap observations can fit existing driver accounting, while the 256 MiB and 1 GiB cases add a charge close to requested size and retain most of that charge after teardown. The same large case has process-ledger footprint and RSS that differ substantially. These observations establish accounting over the observed lifetime, with incomplete independent repetitions, under reported compression and swap. They leave driver pools, caching, mappings billed elsewhere, transient copies and actual physical-page identity open. A dropped CPU-only allocation is a useful control for process accounting, but carries no information about uncharged GPU domains.

The historical M5 1 GiB fixture copied chunks into one readback region and compared the final chunk's first word. Its command stream requests consumption of the entire buffer, while its oracle directly verifies just that last word. This limits what it can establish about actual work performed. The retained output has no complete independent set of vmmap stages and no raw timing samples for the two dirty runs. Keep the prior comment's numbers as attributed historical results.

## Pooling and #464

A's corrected pool trace distinguishes warm allocation/free call timing from cold setup and unused slab capacity. Its real delayed-retirement gate is more meaningful than a future value inserted into the CPU model. The omitted-copy exit is the expected guard/interior mismatch. A smaller warm call cost on the one M4 does not by itself quantify whole-application residency, fragmentation or retained driver memory.

At [PR #486 head 6308fdc](https://github.com/MacosPorters/betterxen/pull/486), the code already validates a 64 KiB grid, resource allocation alignment and the overflow-safe heap span. The reported PR execution is CrossOver 26.2 vkd3d. Treat this M5 D3DMetal study as research for the implementation, without attributing its results to the PR executable. The PR publishes a Map address. Any 64 KiB or larger xmem alignment promise, fixed-address reservation, alias/scatter view or pre-device ownership requirement must be validated independently. Budget logical bytes separately from the driver-retention envelope.

## Same-source reproduction on M5

At the pinned A revision, I rebuilt both sources with their A-local runner, MinGW GCC 16.2.0 and Apple clang 21. The archived source hashes match A's originals. The file hashes of the rebuilt PEs differ, as expected for separate builds. Both sessions loaded the D3DMetal framework and GPTK D3D12, as confirmed by the loaded-library receipt. Host pressure was Warning.

- Both buffer sessions exited 0 and matched all 18 arrays of 16384 words across the source, inherited and guard outputs. The overlapping pairs had equal CPU and GPU virtual addresses. The disjoint CPU and GPU deltas were both 65536 bytes. Map remainders were 32768 and 16384. See the [alias reproduction](../results/2026-11-27-apple-m5-atesahmet0-b-a-alias-01/receipt.json).
- Each texture session matched all nine mixed-heap data and guard comparisons and all eight render/depth clears. Each exited 1 at the same invalid-placement rejection gate. Wrong heap flags still returned E_INVALIDARG. This is a reproduced failure in the full fixture and reproduced positive results in the named valid subcases. See the [texture reproduction](../results/2026-11-27-apple-m5-atesahmet0-b-a-texture-01/receipt.json).
- The independently implemented B placement case additionally used offset 1 in a 128 KiB heap, making the span fit while keeping alignment invalid. The backend returned S_OK. In a separate session the valid maps happened to be 64 KiB aligned. This variation reinforces the need to check each actual CPU address. Invalid resources had no Map, GPU address lookup or submission. See the [isolated placement controls](../results/2026-11-27-apple-m5-atesahmet0-b-small-03/00-placement/stdout.txt).
- Physical-memory accounting and pooling received source and raw-data review. I did not repeat the large M4 accounting profile under the M5's Warning/Urgent conditions. I independently recomputed three native receipt checkpoints. The 1 GiB CPU-only control was charged 13.19 MiB (settled baseline), 1039.47 MiB (initialization) and 13.45 MiB (device-release checkpoint without a device). The WB graphics process was charged 301.36 MiB (baseline), 1368.32 MiB (GPU-complete) and 1328.02 MiB (after device release). The 64 MiB WB process returned from 341.13 MiB after GPU use to 300.79 MiB after device release, near its 300.62 MiB baseline. These are distinct workload-scoped accounting outcomes. See the [A2 raw accounting receipt](../results/2026-11-26-apple-m4-arths17-a2-memory-partial/receipt.json).
