# Review of the M5 report and baseline source

Reviewed 2026-11-26: [2elliti's comment](https://github.com/MacosPorters/betterxen/issues/473#issuecomment-7201953364) and the actual [baseline source at 9ae6d1e](https://github.com/MacosPorters/betterxen/blob/9ae6d1ee7092b6021aad075531f50ba60de4fd53/docs/research/d3dmetal-zero-copy/probe.cpp). Public API expectations were re-derived from the Microsoft pages below, rather than treating either contributor's conclusions as ground truth. This is a technical source audit, not independent certification of the original author's probe or of the new supplemental code.

## What the M5 report establishes

The reported M5 has 17179869184 bytes RAM, macOS 27.0.1 (26A434), and CrossOver 26.3.0.39832. The report says the baseline source hash matched and all non-timing outcomes agreed with the M4 across five runs. The M5 used win10_64, bx-cli from cc5ce59, an empty shim directory and a 90-second timeout. Our M4 used the shared runner, win11_64 and 30 seconds. The M5 captured libd3dshared, which CrossOver also uses when D3DMetal is disabled; that alone does not identify the D3D12 backend. Its backend attribution therefore remains partial as the author states. This review did not obtain the private second probe or independently inspect the reported M5 raw logs: numerical M5 values below are attributed reports, not newly verified hardware measurements.

| Run | WB 64 KiB | WB 256 MiB | WC 256 MiB | UPLOAD 256 MiB |
| --- | ---: | ---: | ---: | ---: |

Units: average ms/submit; each reported row had 40/40 timed and 5/5 warmup matches. Heap rankings are not stable. Different launch protocols, background polling, one chip of each type and large within-host variation prevent a generational speed comparison. A reproduction of the same source also reproduces any source defect; it is not an independently implemented oracle. The independent second M5 probe's reported AMD Compatibility Mode identity is a useful lead, not proof of physical GPU topology or a second independent data check for CUSTOM WB/L0, which that probe skipped.

## Claim-by-claim API and source assessment

| Material claim | Re-derived assessment and public primary reference |
| --- | --- |
| CPU-visible L0 CUSTOM heaps are UMA-only | Incorrect; 2elliti's correction is supported. For UMA=false, UPLOAD maps to WRITE_COMBINE/L0 and READBACK to WRITE_BACK/L0. DEFAULT maps to NOT_AVAILABLE/L1. Successful L0 creation does not establish awareness of physical unified memory. [GetCustomHeapProperties](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12device-getcustomheapproperties%28uint_d3d12_heap_type%29). |
| L1 control distinguishes physical architectures | It does not. L1 is unavailable on UMA; CPU-visible L1 is invalid on NUMA. E_INVALIDARG is the observed runtime result, not a promise that every implementation must return exactly that HRESULT. [Memory pools](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ne-d3d12-d3d12_memory_pool), [heap properties](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ns-d3d12-d3d12_heap_properties). |
| Check 5 measures allocation-sized transfer cost | Source inspection confirms only two 64-byte copies. The allocation's size changes the final source address, not copied byte count. Its timer also includes CPU stores, reset/encoding, barriers, fence wait and verification. [CopyBufferRegion](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12graphicscommandlist-copybufferregion). |
| UPLOAD and CUSTOM benchmark times are directly comparable | Source inspection confirms two source-state transitions for CUSTOM and none for UPLOAD. GENERIC_READ includes COPY_SOURCE and UPLOAD must remain in it. The baseline cannot fairly rank heap types. Supplemental dirty tests use GENERIC_READ for all sources and reuse pre-recorded command lists with no source barriers. [Resource states and barriers](https://learn.microsoft.com/en-us/windows/win32/direct3d12/using-resource-barriers-to-synchronize-resource-states-in-direct3d-12). |
| The timing rules out full-allocation copies | Too strong as a general mechanism claim. 256 MiB / 120 billion bytes/s is about 2.237 ms, but 120 GB/s was not measured here and is not a D3D12 guarantee. Read/write traffic, work overlap, caching, residency, compression and copying before the timing window matter. The source only establishes the observed elapsed times. Neither a theoretical bandwidth estimate nor flat timing proves physical sharing. |
| Persistent-map coherence proves physical aliasing | No. Public D3D12 permits persistent mapping of CPU-accessible resources with application synchronization. CPU stores must complete before GPU execution, and the CPU must wait for GPU completion before reading its results. The baseline's fence-separated visibility can also be implemented by copies. [Map](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12resource-map), [SetEventOnCompletion](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12fence-seteventoncompletion). |
| UNKNOWN texture Map supplies no ordinary texel pointer | The baseline asks for no pointer at all: ppData=nullptr. Thus it never measured a pointer-return failure. Microsoft describes opaque layouts as precluding pointer disclosure for normal texel manipulation; Map with null ppData enables the CPU subresource methods. Do not infer an ordinary guest-pointer alias for such textures. [Map](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12resource-map). |
| Every texture therefore requires an explicit staging copy | Not established. WriteToSubresource permits CPU texture updates and documents possible near-zero-copy UMA optimizations. That does not guarantee the implementation's internal mechanism. Texture GPU readback must be tested separately, with layout/format constraints; ROW_MAJOR is not a general substitute for opaque layout. [WriteToSubresource](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12resource-writetosubresource), [ReadFromSubresource](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12resource-readfromsubresource). |
| ROW_MAJOR creation success on an ordinary CPU-visible heap is portable evidence | No. The layout documentation requires a cross-adapter shared heap and limits textures to 2D, one mip/slice, 64 KiB alignment, no MSAA, no depth/stencil, no YUV. Phase two uses a DEFAULT shared-cross-adapter heap and ALLOW_CROSS_ADAPTER resource for this separate staging-copy control. It never reports a fabricated Map result when Map was not called. [Texture layouts](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ne-d3d12-d3d12_texture_layout), [shared heaps](https://learn.microsoft.com/en-us/windows/win32/direct3d12/shared-heaps), [resource flags](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ne-d3d12-d3d12_resource_flags). |
| 0/16384 write-watch writes test 4 KiB subpages | No; they address different 16 KiB intervals. Separate tests at 4096, 8192, 12288 and the 16383/16384 boundary are required. GetWriteWatch reports dirty page addresses and its own granularity; reset tests must exclude concurrent writes. [GetWriteWatch](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-getwritewatch). |
| IsolatedMMU=false proves GPU writes cannot be reported by write-watch | Too categorical. TRUE indicates GPU honoring of CPU page-table properties; FALSE supplies no such guarantee. A translation implementation could still cause CPU-side bookkeeping or copies that mark pages. A fallback must not rely on GPU writes being tracked, but absence of tracking cannot be inferred as a universal measured fact from this flag. [Architecture1](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ns-d3d12-d3d12_feature_data_architecture1). |
| 1x/2x footprint or a vmmap region label proves allocation identity | It does not. These are process-accounting observations influenced by graphics/driver charging, shared mappings, compression, allocator caches and sampling. A controlled slope across fully initialized sizes can reveal overhead in the observed accounting domain, but cannot identify physical pages or uncharged driver allocations. Microsoft's DXGI memory descriptions/budgets are also not a physical-page aliasing API. [DXGI adapter description](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/ns-dxgi1_2-dxgi_adapter_desc2), [QueryVideoMemoryInfo](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_4/nf-dxgi1_4-idxgiadapter3-queryvideomemoryinfo). |
| Dirty-k timing slope alone identifies internal dirty-page copies | No. It can expose a cost correlated with changed pages, but CPU page faults/tracking, cache behavior, transfer at other times and scheduling are alternative explanations. Phase two records dirty-write time separately, times identical submit/fence work and validates checksums outside the window. |
| OpenExistingHeapFrom* is the natural bridge on this installed stack | These public diagnostic APIs can expose system-memory heaps, but both observed versions returned E_NOTIMPL. Availability in Microsoft documentation does not imply implementation by D3DMetal. [Address API](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12device3-openexistingheapfromaddress), [mapping API](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12device3-openexistingheapfromfilemapping). |

The shared-heaps page itself has inconsistent wording about CPU page properties for cross-adapter heaps (a paragraph mentions WRITE_COMBINE; the subsequent limitations require DEFAULT or NOT_AVAILABLE/L0). This suite uses the unambiguous DEFAULT option, does not attempt CPU Map on that control, and does not generalize its result to CPU-visible shared heaps.

## Additional baseline audit observations

- Its six checks remain unchanged. Unsupported HRESULTs often return from a helper without incrementing the mismatch counter; exit 0 is not all-capabilities-supported. Read each result rather than the final counter alone.
- Its 64 KiB prefault stride does not fully initialize the intervening host pages. Phase-two footprint tests write every 32-bit word with an index-mixed pattern instead.
- The buffer coherence test performs copies, not shader reads/writes. The new shader test poisons the result before each dispatch, then validates three separate data rounds. An omitted-dispatch negative control must be detected.
- Resources remain live through their fences. The baseline uses disjoint placed-resource regions rather than switching overlapping aliases. CreatePlacedResource's advanced model permits non-overlapping use without the simple model's activation bookkeeping; it does not excuse missing barriers when memory is actually aliased. [CreatePlacedResource](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12device-createplacedresource).
- No GPU texture readback, arbitrary-memory integration, lifetime stress, memory-overhead study, GPU write-watch tracking or valid concurrent CPU/GPU atomic protocol can be inferred from the baseline.

The proposed concurrent-visibility experiment is assessed separately in [concurrent-review.md](concurrent-review.md). It is not a conformance gate and is not executed by the standardized synchronized suite.
