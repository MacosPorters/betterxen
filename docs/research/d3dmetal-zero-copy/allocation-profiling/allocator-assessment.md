# Optional allocator reference assessment

Reviewed 2026-11-26: AMD's [D3D12 Memory Allocator](https://github.com/GPUOpen-LibrariesAndSDKs/D3D12MemoryAllocator/tree/600949266be004553f74c9ef809384380a9d44cf), exact commit `600949266be004553f74c9ef809384380a9d44cf`; the pinned header reports version 3.3.0. This is a public, general-purpose GPUOpen allocation library, with no game/console material used in this assessment.

The exact files reviewed were [LICENSE.txt](https://github.com/GPUOpen-LibrariesAndSDKs/D3D12MemoryAllocator/blob/600949266be004553f74c9ef809384380a9d44cf/LICENSE.txt), [include/D3D12MemAlloc.h](https://github.com/GPUOpen-LibrariesAndSDKs/D3D12MemoryAllocator/blob/600949266be004553f74c9ef809384380a9d44cf/include/D3D12MemAlloc.h) (Git blob `b685a5cd6188519606efaf039cd88c2faffa261a`) and [src/D3D12MemAlloc.cpp](https://github.com/GPUOpen-LibrariesAndSDKs/D3D12MemoryAllocator/blob/600949266be004553f74c9ef809384380a9d44cf/src/D3D12MemAlloc.cpp) (blob `b7ba60a3a4deb0ed466b235b7c5298f91ba5c976`). Both source files carry the full AMD 2019–2026 MIT notice. The MIT grant permits use/modification/distribution while requiring preservation of its notice; it is compatible with inclusion in a GPL-3.0-or-later work under those obligations. This does not license CrossOver/D3DMetal/Rosetta or change their external status.

At the initial assessment, no source from this project had been copied, compiled, linked, modified or adopted. The resumed isolated experiment below supersedes that build/runtime status; no source is adopted in production. A's small first-fit trace allocator is original experimental code, not an alternative production allocator. Exact registry/reuse-matrix entries and preserved upstream notices are required before any future source integration; that would be a separately scoped decision.

Initial recommendation was to evaluate this reuse candidate with an externally built pinned version before selection; the later isolated study below partially supplies that evidence. Raw-D3D12 pooling results cannot be presented as this allocator's performance, fragmentation quality or CrossOver compatibility. Documentation/source assessment is class D (project evidence); public D3D12 contracts are class B. Independent review and runtime qualification remain pending.

## Resumed isolated evaluation

After per-file notice revalidation and registry/reuse-matrix entries, exact unmodified files were obtained into ignored artifacts and verified against their Git blobs. Python urllib initially failed TLS certificate verification before obtaining bytes; normal verified curl succeeded. TLS verification was not disabled. The original [evaluation harness](allocator-evaluation/README.md) compiled cleanly with strict flags.

A [WB/WC pilot](../results/2026-11-26-apple-m4-arths17-external-allocator-pilot/receipt.json) ran when kernel pressure improved to the explicitly permitted Warning profile. Each fresh process completed 24 guard/interior readbacks across two warmup plus ten measured cycles. Library statistics stayed at one 33,554,432-byte block and returned zero live allocation bytes/count with largest free span equal to the block size at every empty checkpoint. The pilot's seed-473 payload/phase/slot sequence matches all 432 published raw-trace allocation requests. Combined CreateResource median was 0.0011 ms in both pilot types; this is a different API aggregation/session from the earlier raw allocator, not a controlled speedup claim.

This is new version-scoped author-run buffer/pool/statistics evidence, not qualification of every D3D12MA feature. Caller-managed fence/command retirement remains necessary. Texture allocation through the library, multi-queue use, defragmentation/migration, device-loss handling, all heap-tier restrictions and independent review remain open. The separately recorded bounded-request/repeated-seed run is described below. Registry source notices and external/no-production boundaries are unchanged.

## Repeated bounded-buffer result

[Six fresh processes](../results/2026-11-26-apple-m4-arths17-external-allocator-bounded/receipt.json) alternated WB/WC order across seeds 473/474/475. Every process exited 0 without a timeout. All 24 readback events per process matched 1152/1152 sampled leading/interior/trailing words; this samples each buffer, rather than verifying every initialized byte. The valid 33,554,436-byte request returned E_OUTOFMEMORY (0x8007000E) in all six cases without growing the single 32 MiB pool. Caller-managed completed fences and command reset precede each release.

The separate [analysis program](allocator-evaluation/analyze.py) derives free gaps from recorded live intervals, checks bounds/overlap and every reported full/holes/empty statistic, and compares each phase/slot/request size with the original corrected raw-pool seed. All 432 allocation requests per process matched; 36 statistics checkpoints per process matched the independent interval calculation. Both producer and checker are author work and remain subject to independent contributor acceptance. Empty checkpoints consistently reported zero live allocations with 33,554,432 bytes as the largest free range; block retention is explicitly configured, not a measured leak.

Measured CreateResource medians were 0.00105–0.00110 ms and whole-cycle medians 9.73–10.00 ms across these sessions. CreateResource combines library allocation and D3D12 placement. Earlier raw allocation-call costs are separate API boundaries, and the sessions were non-idle under existing swap and warning pressure. No controlled performance superiority, physical memory savings, automatic queue-fence retirement, texture/heap-tier qualification or production adoption follows from these data.
