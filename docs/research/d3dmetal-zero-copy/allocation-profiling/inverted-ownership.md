# Inverted ownership feasibility

This requirement matrix informs [#464](https://github.com/MacosPorters/betterxen/issues/464) without modifying or certifying it. The inspected in-tree contracts are pinned at research revision `9ae6d1ee7092b6021aad075531f50ba60de4fd53`: `abi/include/bx_xmem_internal.h`, `shims/xmem/xmem.cpp`, `shims/xmem/physical_pages.cpp` and `abi/defs/xmem.def`. They describe BetterXen's implementation, not an independently verified console allocation contract. Memory-attribute meanings not established by public evidence remain unknown.

A D3D12-owned mapped buffer is a candidate provider for a subset of allocations. It is not a general replacement for the present xmem allocation engines.

XMemVirtualAlloc and physical map paths accept one. | VirtualAlloc/placeholder/section mechanism; logged explicit graphics transfer where needed. Do not relocate a guest allocation silently. |

[Resource and lifetime contracts](../gpu-correctness/contracts/resource-placement-lifetime.md) link primary D3D12 documentation. Local observations are class A within their workloads; public API constraints class B; compatibility with unverified console semantics and physical backing remain class U. No production adoption is recommended solely from these synthetic checks.

## Alignment, contents and budget decisions after the resumed review

Let a mapped buffer base be P, a byte-slice offset be d and the required CPU alignment be A. CPU alignment requires `(P + d) mod A = 0`. A placed resource beginning at heap offset d separately requires `d mod resource_alignment = 0`. When A and resource_alignment are both 64 KiB and P has the observed 16 KiB or 48 KiB remainder, no 64 KiB-multiple offset solves both requirements. Adding an aligned heap offset cannot repair the base pointer. Padding/biasing can only be a candidate for a byte slice *inside* a legal buffer, with its own bounds, view/descriptor alignment, GPU offset and lifetime validated; it cannot be treated as a new legally placed resource at that biased offset. Two MiB pointer padding likewise does not establish two MiB physical sections or page identity. No combined CPU/GPU-offset qualification is claimed by the earlier +64 KiB alias observation.

Existing contents and guest pointer identity are separate requirements. An allocation selected for a D3D12 provider before exposing its pointer could use that provider's lifetime. An already exposed CPU allocation cannot silently move to a new Map pointer. Copying its bytes to graphics storage preserves a snapshot of contents under synchronization, but preserves neither pointer identity nor CPU section aliases. Without an existing-memory wrapping interface, keep the original owner and an explicit transfer boundary. CPU-only and pre-device allocations therefore retain conventional CPU allocation. UNKNOWN textures retain format-aware upload/readback paths; CPU-visible texture success does not make them ordinary mapped byte arrays. DEFAULT storage is a correctness-tested option, with relative bandwidth and physical cost still awaiting B's evidence.

| Accounting layer | Required treatment |
| --- | --- |
| Guest logical payload | Track each live allocation once, including size, attributes and owner. A slice and its containing slab are related records, not two payload charges. |
| Reserved backing | Track slab capacity, live/pending suballocation reservations, alignment waste, total free span and largest usable span separately. Fixed bounds can reject requests despite sufficient total fragmented space. |
| Pending GPU retirement | A guest free can remove live payload while storage remains unavailable until all final-use fences complete. The real queued-copy trace and the logical delayed-retirement model cover different parts of this requirement. |
| Migration peak | Old backing remains charged until retired, while new backing is also reserved. A transfer does not temporarily make either backing free. Fixed guest pointers can rule out migration entirely. |
| Host process/driver | Observe footprint, resident/compressed/swapped accounting and retained driver charges independently. Logical free/reusable spans do not imply physical release, nor do retained driver charges alone prove a leak. |

The bounded allocator experiment supports one optional implementation candidate for the feasible buffer rows. It cannot add requested virtual addresses, decommit, section handles, physical tags, scatter semantics or device-independent ownership. An eventual production design needs explicit per-requirement eligibility and fallback, then independent review; there is no blanket recommendation to route xmem through D3D12.
