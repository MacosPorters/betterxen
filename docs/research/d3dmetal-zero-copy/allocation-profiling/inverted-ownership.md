# Inverted ownership feasibility

This requirement matrix informs [#464](https://github.com/MacosPorters/betterxen/issues/464) without modifying or certifying it. The inspected in-tree contracts are pinned at research revision `9ae6d1ee7092b6021aad075531f50ba60de4fd53`: `abi/include/bx_xmem_internal.h`, `shims/xmem/xmem.cpp`, `shims/xmem/physical_pages.cpp` and `abi/defs/xmem.def`. They describe BetterXen's implementation, not an independently verified console allocation contract. Memory-attribute meanings not established by public evidence remain unknown.

A D3D12-owned mapped buffer is a candidate provider for a subset of allocations. It is not a general replacement for the present xmem allocation engines.

| Requirement | Evidence / feasibility | Necessary fallback or further work |
| --- | --- | --- |
| Ordinary CPU-visible byte allocation | Persistent buffer Map supported in baseline; A2 full-consumption checks add accounting evidence. Candidate within live resource lifetime. | Keep owner/resource metadata and explicit synchronization; independent acceptance pending. |
| 64-byte alignment of XMemAllocDefault | Existing xmem heap returns 64-byte-aligned data. Biased byte slices can potentially satisfy this inside a sufficiently sized buffer. | Validate buffer offsets and bounds; do not change production in this research. |
| 64 KiB resource placement | GetResourceAllocationInfo and aligned heap offsets determine GPU placement. | Not a CPU-pointer alignment guarantee. |
| 64 KiB CPU pointer | New M4 64 MiB WB and UPLOAD maps observed at 16 KiB modulo 64 KiB. Unconditionally handing out the base does not satisfy this requirement. | Overallocate and bias byte slices only where guest/GPU address-offset contracts permit it; otherwise CPU-owned allocation and explicit transfer. |
| 2 MiB CPU alignment/page size | Physical-page engine supports flagged 2 MiB sections; no D3D12 Map promise provides this CPU alignment or page identity. | Preserve section-backed path; extra padding alone does not provide physical-page semantics. |
| Requested CPU virtual address | CreateHeap/CreatePlacedResource/Map provide no requested CPU-VA parameter. XMemVirtualAlloc and physical map paths accept one. | VirtualAlloc/placeholder/section mechanism; logged explicit graphics transfer where needed. Do not relocate a guest allocation silently. |
| Reserve now, commit/decommit later | In-tree XMemVirtualAlloc forwards MEM_RESERVE/COMMIT/RESET and tracks commits; decommits are reconciled with VirtualQuery. A mapped D3D12 buffer is not an interchangeable reservation. | Keep CPU VA reservation path. GPU reserved resources are a separate GPU-VA concept, not proof of CPU-VA equivalence. |
| Win32 protection/guard/cache flags | In-tree xmem normalizes a subset of page protections and flags. CPU cache property selection exists in CUSTOM heaps, not a general VirtualProtect/page-guard contract. | Preserve unsupported combinations on CPU path, retain original attributes rather than infer their console meaning. |
| Caller-owned allocation made before device creation | No D3D12 buffer can exist before its device. Both existing-memory heap opens returned E_NOTIMPL in published baseline observations on these runtime versions. | CPU allocation plus explicit copy; do not move a live pointer after creating the device. |
| Physical tags and multiple CPU aliases | Physical engine owns file-mapping sections, stable tags and independently placed CPU views. Public D3D12 GPU heap aliasing does not expose equivalent section handles or arbitrary CPU aliases. | Retain section-backed pages and translation/copy boundary; alias correctness is not solved by Map. |
| Scatter mappings/reordered page views | In-tree contiguous/scatter entry points both route through section/placeholder view logic; D3D12 Map alone exposes no equivalent requested CPU scatter mapping. | Preserve engine; future bridging requires a demonstrated interface, not pointer arithmetic. |
| xmem region query | Current bx_xmem_query_region describes physical mapped views, verifies MEM_MAPPED, and returns page tag/protection/type. Ordinary virtual and D3D12 allocations are not automatically registered. | Any future cross-DLL provider metadata would need separate maintainer/ABI work outside #473. |
| Unified logical budget | Current xmem tracks virtual commits/heap bytes/physical pages; D3D12 allocations outside it are not automatically included. | One logical owner/charge, bounded slab reservation and retirement accounting; host footprint/headroom tracked separately. Do not double-charge a live slice and its slab. |
| GPU lifetime while guest frees pointer | Resource/heap/mapped pointer must survive last GPU use; A tests explicit delayed retirement. | Queue/fence retirement records, no reuse or pointer access after disposal. Multi-queue/reference stress remains open. |
| Texture placed over arbitrary CPU pointer | UNKNOWN texture layouts are opaque; buffer sharing does not supply a raw texel alias or console tile mapping. | Explicit texture upload/readback APIs and format/layout handling; do not assume every internal texture path copies. |

[Resource and lifetime contracts](../gpu-correctness/contracts/resource-placement-lifetime.md) link primary D3D12 documentation. Local observations are class A within their workloads; public API constraints class B; compatibility with unverified console semantics and physical backing remain class U. No production adoption is recommended solely from these synthetic checks.
