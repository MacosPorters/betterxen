# Synchronization, mapping and write tracking

Workstream B contract review for [#473](https://github.com/MacosPorters/betterxen/issues/473) and [#464](https://github.com/MacosPorters/betterxen/issues/464). Public D3D12 and Windows contracts are class B. The [probe and result guide](../../copy-detection/README.md) records version-scoped local observations and the status of reciprocal review.

## Ordering and lifetime

- Finish CPU stores before the GPU submission that can read them. For this x86-64 guest, the fixtures order the stores before submission with an SFENCE. The caller owns ordering between CPU producer threads and the thread that submits. For CPU reads of GPU-written data, wait for the fence value signaled on the consuming or writing queue. Treat a failed wait, timeout or device-removed fence as a failed run. [Map contract](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12resource-map).
- On one queue, place the fence signal after the relevant execution. A CPU-side fence signal cannot establish GPU completion. Across queues, signal the producing queue and wait on the consuming queue before dependent commands. Keep the queue-specific resource state requirements and use one progress timeline per fence where possible. [Multi-engine synchronization](https://learn.microsoft.com/en-us/windows/win32/direct3d12/user-mode-heap-synchronization).
- Persistent mapping of CPU-accessible resources is supported. Keep the resource alive as long as the pointer is used and retire commands before reclaiming memory or overwriting ranges still in use. Map and Unmap ranges convey CPU access information for tools. Persistent access does not wait for the GPU, guarantee a stable pointer across resource destruction, or imply concurrent CPU/GPU atomic interoperability. Use Map with a null output for CPU subresource access to opaque textures where the API supports it. [Map](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12resource-map), [WriteToSubresource](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12resource-writetosubresource).
- Complete outstanding GPU use before releasing heaps, resources, descriptors, command allocators or mapped storage they reference. For reusing an overlapping span, retire the last use and apply the aliasing rules for the new resource. For GPU-queued reuse without a CPU wait, enforce the dependency on the participating queues. [Resource barriers](https://learn.microsoft.com/en-us/windows/win32/direct3d12/using-resource-barriers-to-synchronize-resource-states-in-direct3d-12), [placed-resource usage](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12device-createplacedresource).

## States and aliases used in this research

| Operation | Contract used |
| --- | --- |
| Buffer copied from or read as a shader resource | Use COPY_SOURCE or NON_PIXEL_SHADER_RESOURCE. COMMON buffers may promote implicitly to these read states. Implicitly promoted buffers decay at completed ExecuteCommandLists operation boundaries. STANDARD UPLOAD remains GENERIC_READ, which includes these states. |
| GPU copy into readback | READBACK stays COPY_DEST. Map may remain live and CPU consumes bytes after the fence. |
| Shader UAV output | Transition to UNORDERED_ACCESS before the dispatch. Transition from UAV to COPY_SOURCE before a dependent readback copy, or restore COMMON for the next submission. When dependent UAV accesses remain in UAV state, order them with a UAV barrier. |
| Mixed placed buffer and texture | Use heap tier and flags appropriate to both resources. Use allocation-info alignment and size for the heap span. Use copyable footprints for buffer offsets and row pitches, and apply states per resource or subresource as needed. |
| Overlapping render/depth textures | Activate the new alias at the execution boundary or via the appropriate alias barrier. In the simple model, initialize each RT/DS resource after activation using an allowed clear, discard or full subresource copy before other uses. |
| Buffer alias inheritance | The advanced model permits inheritance in documented compatible overlapping layouts. Establish ordering with an alias barrier inside one Execute operation or with the documented separate Execute operation boundary. Verify distinct guard data and do not extrapolate across layouts. |

[Resource state promotion, decay and barrier rules](https://learn.microsoft.com/en-us/windows/win32/direct3d12/using-resource-barriers-to-synchronize-resource-states-in-direct3d-12), [aliasing and data inheritance](https://learn.microsoft.com/en-us/windows/win32/direct3d12/memory-aliasing-and-data-inheritance), [placed-resource lifetime and initialization](resource-placement-lifetime.md).

D3D12 placement alignment constrains a heap-relative byte offset. Validate candidate offsets and spans before creation with checks equivalent to `offset % alignment == 0`, `offset <= heap_size` and `allocation_size <= heap_size - offset`. A CPU virtual pointer has its own alignment. Biasing a CPU pointer within a mapped buffer can align that pointer, but a separately placed resource at the matching biased heap offset may violate placement requirements. A constant whole-heap offset on a 64 KiB grid cannot change the mapped base's remainder. [CreatePlacedResource](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12device-createplacedresource).

## Write tracking

GetWriteWatch and ResetWriteWatch require a region reserved with VirtualAlloc and MEM_WRITE_WATCH. Use returned granularity and address offsets, and track application ownership of each dirty range. To use these pages as the source of an explicit selective copy, quiesce writers or establish coherent per-range ownership over collection, reset, snapshot/copy, and reuse. A separate GetWriteWatch followed by ResetWriteWatch can drop writes in the middle. Combining collection and reset still leaves races with data copying when writers can modify the same bytes concurrently. Retry paths must retain or conservatively restore dirty coverage. [GetWriteWatch](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-getwritewatch), [ResetWriteWatch](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-resetwritewatch).

A 4 KiB guest report can distinguish stores within a 16 KiB host page. That observation describes the Windows API on the tested Wine version. It does not establish the tracking implementation's physical granularity. A D3D12 Map address has no demonstrated MEM_WRITE_WATCH allocation contract. GPU stores remain untracked unless an independently validated mechanism is available. IsolatedMMU TRUE states a GPU guarantee regarding CPU page-table properties, with documented granularity and false-positive caveats. FALSE supplies no guarantee and cannot establish a universal absence of GPU-related dirty reports. Application-managed flags or shader instrumentation can cover known writers and ranges. Arbitrary GPU writes require a separate supported mechanism or conservative copies. [Architecture1](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ns-d3d12-d3d12_feature_data_architecture1).

Apple's public Metal shared resource contract governs applications that create resources with that storage mode and coordinate access. It cannot identify an opaque D3D12 translation's storage or exclude internal copies. [Metal shared storage](https://developer.apple.com/documentation/metal/mtlstoragemode/shared).
