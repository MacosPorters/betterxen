# Texture and placed-resource fixtures

Workstream A extends the frozen baseline and preserved M4 supplemental texture check for [#473](https://github.com/MacosPorters/betterxen/issues/473). [The inventory](../../allocation-profiling/inventory/README.md) records the already tested 65x37 RGBA8 one-mip UNKNOWN and valid ROW_MAJOR cross-adapter controls; their identical experiments are not newly commissioned here. [Resource/lifetime notes](../contracts/resource-placement-lifetime.md) derive expected behavior from primary D3D12 documentation. Independent review is pending.

Run `../../allocation-profiling/run.py --suite texture` with the documented `--bottle` and a fresh external `--scratch` directory. It compiles this original `probe.cpp`, performs two fresh-process sessions with different datasets, and archives raw results, exact source/PE hashes, commands, backend evidence and failures. `--smoke` performs one session. No shader is needed by these copy/clear cases, so shader hashes are not applicable.

New cases use 65x37 textures with three mip levels in RGBA8, R8_UNORM and R32_UINT, on CUSTOM/WB/L0, CUSTOM/WC/L0 and DEFAULT heaps. Each texture coexists with a disjoint 64 KiB buffer on the same Tier-2 heap. Every buffer guard word and every actual mip texel byte is compared after GPU readback. CPU-visible textures use per-subresource Map with a null output pointer and WriteToSubresource in COMMON. DEFAULT textures are initialized through a footprint-pitched UPLOAD buffer. Copy footprints use a nonzero 512-byte base offset, padded row pitches and separately checked unpadded row sizes. These transfer layouts do not reveal opaque texture storage.

Separate RGBA8 render-target and D32_FLOAT depth cases place two resources at the same heap offset on WB and DEFAULT heaps. Within one command list, activate A, clear/initialize it, copy it out, then activate B with an A-to-B aliasing barrier, clear B and copy it out. Exact endpoint colors (0/1) and exactly representable depth values (0.5/0.25) have fixed expected bits. No previous alias contents are assumed. This tests clear/copy/alias behavior, not rasterized depth testing, stencil or sampled filtering.

Negative creation checks ask for misaligned and out-of-bounds buffer placements and a texture on a buffer-only heap. An unexpected success fails our rejection gate and is never permission to use that invalid resource; caller-invalid calls do not independently establish a conformance violation. Unsupported creation/CPU-access paths print exact HRESULT and explicit not-run status; exit 0 alone does not mean every configuration worked. Read each outcome.

MSAA, compressed/planar formats, arrays/3D, texture reinterpretation and console tiling are not covered by these fixtures. The later graphics supplement below has narrower sampling/depth/stencil observations. They remain explicit gaps, and are not inferred from successful copies or clears. In particular, neither a null ppData request nor readback agreement establishes that raw xmem pointers alias texture pixels. DEFAULT versus CUSTOM cases do not identify D3DMetal's internal Metal storage mode or measure its bandwidth.

The follow-up alias.cpp (run with --suite alias) tests valid buffer data inheritance under the advanced model, with two overlapping buffers and a disjoint guard, three changing GPU-write rounds per session and no raw CPU alias dereference used as a GPU oracle. Exact Map-pointer/GPU-VA relations are recorded as observations. See [findings](findings.md) for the distinction between the passing positive readbacks and failed negative-rejection gate.

## A-local-2.3 graphics supplement

The original `render.cpp` adds a graphics pipeline with a shader-resource view, point/clamp sampling and a full-screen triangle. It uses authored Shader Model 5.0 HLSL compiled by the externally installed shader compiler. Per-process HLSL/DXBC bytes and hashes are retained. It does not implement B's compute access, copy-detection or synchronization studies.

```sh
python3 docs/research/d3dmetal-zero-copy/allocation-profiling/run.py --suite render --bottle /absolute/path/to/win64/bottle --scratch /tmp/bx473-render-review
python3 docs/research/d3dmetal-zero-copy/gpu-correctness/textures-and-resources/check-render.py /tmp/bx473-render-review --output /tmp/bx473-render-oracle.json
```

The full profile requests two fresh processes with changing endpoint-color palettes. Source textures are 16x16 RGBA8 on CUSTOM WB/L0, CUSTOM WC/L0 and DEFAULT. CPU-visible textures use null-pointer Map plus WriteToSubresource; DEFAULT uses upload/copy. A 32x16 DEFAULT render target is read back after the completed fence and every pixel is compared. One-to-two horizontal scaling with point sampling has fixed quadrant colors; no tolerance or interpolation approximation is used. Additional DEFAULT D32_FLOAT cases clear depth to 0.5, reject z=0.75 and accept z=0.25 under LESS. DEFAULT D24_UNORM_S8_UINT cases clear stencil to zero, increment it with a color-write-disabled triangle, then reject reference 2 and accept reference 1 under EQUAL. Both face states agree. This covers one stencil operation near zero, not saturation edges or every operation.

Run the separate omitted-draw negative control using the same command with a new scratch directory and `--negative-control`. The guest must exit 1 specifically for a pixel mismatch; the checker expects 512 mismatches against the required sampled image. Packed raw `.rgba` frames enable separate recalculation without importing the C++ pixel routine. The checker rejects empty/stopped profiles. The earlier corrected smoke precedes raw frame capture and cannot be retrospectively checked this way. Results, the initial probe bug and pressure-stopped repeat are preserved in [findings](findings.md).

Every unsupported creation or pipeline path is a failure with its exact HRESULT, not a skipped success. There is no feature-wide acceptance or inference about UNKNOWN storage's internal representation, sampled mips/filtering, MSAA, other formats or console tiling. Independent source review and critical reproduction remain required.
