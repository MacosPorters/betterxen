## Shader decision and legitimate compiler path

The runtime consumes ordinary Windows shaders through CrossOver. `launcher/crates/bx-runtime` has no dependency on the console shader import. #394's compiler therefore solves no demonstrated requirement of this execution path. The complete per-file [independent #399 review](https://github.com/MacosPorters/betterxen/issues/399) and [donor decision proposal](https://github.com/MacosPorters/betterxen/blob/b42133add913297690dbade1941916f4ce0b666a/docs/research/shader-import-decision.md) identify unresolved origin and explicit project-policy exclusions. This candidate excludes #394 and the dependent #395 runner. Passing compiler tests cannot resolve those exclusions; no replacement console compiler is required.

Only the seven original `tests/conformance/test_d3d12_wave/` files from BetterXen commit `d8c7a398492c483599f02766ebf5707f38dc6128` are retained. The C runner has bounded inputs and releases successful-run resources; the build adds the missing GUID library. Numeric acceptance compares GPU words with independent arithmetic constants and checks a one-bit wrong expectation. Unsupported double precision is not counted as a pass.

Microsoft DXC is an external open-source **Windows guest build tool**, not a BetterXen x86-64 host executable. The selected release is [v1.9.2609](https://github.com/microsoft/DirectXShaderCompiler/releases/tag/v1.9.2609), asset `dxc_2026_09_29.zip`, SHA-256 `ad31b1fc8443175d204f77a611fdb3ef2ec42759bdc2f1167368de24a4a7e7f1` (verified against GitHub release metadata). Its LLVM/MIT/Microsoft notices stay with the external installation. No compiler DLL or executable is packaged. Original HLSL and its compiled output are separate from the excluded console compiler. The installer must verify the archive before use.

The external llvm-mingw pin remains release `20261117`, SHA-256 `98d340bbb8d46b09ad6886ffba88bd9d5415e131c316de48e6bd7647377446aa`, LLVM commit `5b10d2d74929eae78912771222c9855af97496f4`. Its wrappers are ISC; compiler, builtins, headers and runtime carry their own notices. The universal compiler is run natively on ARM64 and is not distributed. Build notices include the unmodified LLVM and MinGW runtime terms. Rust Windows COFF timestamps are explicitly disabled; source paths are remapped. The original independent #364 build review remains separate from this task.

The current engineering rules require a recorded per-file provenance and licence audit before taking any code or tooling from leaked-build derivatives, and exclude game-, asset- and decryption-specific code. Contributor permission covers only contributions the contributor owns. This candidate takes no additional source from those projects; the inherited Rust memory guard is an attributed conceptual reimplementation from #405, with the original per-component review preserved in its donor audit. The current Track D shader-format gate remains separate from the excluded #394 import. No policy amendment is needed for the current Windows shader probes.

## Accessibility check and limits

All 23 requested GitHub repositories were reachable during this task; public heads are saved in the [accessibility snapshot](maintainer-reference-heads.json), with authenticated private metadata kept in ignored local evidence. The existing 84-entry PortWatch inventory was not repeated. Except for the source files identified above, those checks are metadata only, not implementation review. LLVM, llvm-mingw, DXC, DirectX-Headers, DirectXTex, DirectX-Graphics-Samples, SPIRV-Cross, wgpu, LIEF, FEX and apitrace remain available references; none supplies a demonstrated missing loader, translator or backend for this candidate merely by being available.

The [CodeWeavers source page](https://www.codeweavers.com/crossover/source) publishes `crossover-sources-26.3.0.tar.gz`. This task downloads that official archive for targeted source comparison; downloading is not a rebuilt or validated replacement runtime. CodeWeavers' [graphics documentation](https://support.codeweavers.com/advanced-settings-in-crossover-mac?kb_language=en_US) separates D3DMetal's D3D11/12 support from DXVK's D3D10/11 role. A `dxvk` or `wined3d` selection must not be labelled proof of the active D3D12 implementation.

Apple's [Metal command execution documentation](https://developer.apple.com/library/archive/documentation/Miscellaneous/Conceptual/MetalProgrammingGuide/Cmd-Submiss/Cmd-Submiss.html) distinguishes submission, completion and presentation. Accordingly, an application fence and matching readback do not establish that pixels reached the compositor; screen capture remains a separate check. None of this establishes Xbox execution, commercial-game compatibility or performance.
